# Deep Research — 深度研究技能

> 将复杂研究问题拆解为子问题，联网搜索并逐一回答，综合结论后验证，最终输出结构化研究报告。

---

## 概述

**Deep Research（深度研究）** 是一个 Reasonix/Claude Code 技能，能将任意复杂研究问题转化为结构化、可验证的研究报告。它遵循严格的 5 步方法论：**拆解 → 研究 → 综合 → 验证 → 输出**。

与简单"问 AI 拿答案"不同，Deep Research 会：

- **拆解**问题为 3–7 个独立子问题
- **联网搜索**逐一研究每个子问题（每批最多 3 个并行）
- **综合**所有发现，提炼核心结论
- **验证**结论，刻意搜索反方观点
- 验证不通过则**迭代**重试（最多 2 轮）
- **输出**带完整来源引用的结构化 Markdown 报告

## 工作流程

```
用户问题
     ↓
Step 1: 问题拆解 → 3~7 个子问题
     ↓
Step 2: 逐子问题研究 (并行，每批最多 3 个)
     ↓
Step 3: 综合汇总 → 初步结论
     ↓
Step 4: 验证 → 设计可证伪的验证要点 → 搜索反方证据
     ↓
Step 5: 通过? → 生成报告文件
        不通过? → 回到 Step 1 (最多 2 次迭代)
```

### Step 1 — 问题拆解

将复杂问题按以下维度拆解为 3–7 个正交子问题：定义/概念 → 现状/事实 → 原因/机制 → 影响/趋势 → 方案/对比。

### Step 2 — 逐子问题研究

对每个子问题联网搜索，可选 `web_fetch` 深入阅读关键页面。提取事实、数据、观点，输出结构化回答并标注来源。

**搜索降级策略：** 连续 2 次搜索返回无关首页/垃圾结果时，切换为 `web_fetch` 直取权威域名（官方文档 > 知名技术博客 > 社区 Wiki）。

### Step 3 — 综合汇总

交叉对照所有子问题答案，提炼 3–5 个核心发现，形成初步结论。明确标注不确定性和信息缺口。

### Step 4 — 验证

设计 3–5 个**可证伪**的验证要点（可以被证明是错的才叫验证）。刻意搜索反例、相反观点或更权威的数据。每个要点判定 ✅ 通过或 ❌ 不通过，附判定依据。

### Step 5 — 输出

| 场景 | 动作 |
|------|------|
| 验证通过 | 生成结构化报告文件（`deep-research-<主题slug>.md`） |
| 验证不通过 + 迭代 < 2 | 回到 Step 1 重新拆解 |
| 迭代到上限仍不通过 | 如实生成报告，标注 ⚠️ 未通过的疑点 |

## 报告结构

生成的报告包含 6 个标准章节，全程可溯源：

| 章节 | 内容 |
|------|------|
| 一、子问题拆解 | 问题分解表 |
| 二、逐子问题研究 | 每个子问题的搜索结果、来源和结构化回答 |
| 三、综合初步结论 | 3–5 个核心发现 + 初步结论 + 信息缺口 |
| 四、验证 | 可证伪的验证要点 + 反向证据搜索 + 逐要点通过/不通过 |
| 五、最终结论 | 验证修正后的最终回答（或标注未解决的疑点） |
| 六、来源汇总 | 所有引用来源及 URL |

## 安装

1. 将 `deep-research/` 目录复制到 Reasonix / Claude Code 技能目录：
   - **项目级别：** `<project>/.reasonix/skills/deep-research/`
   - **全局：** `~/.reasonix/skills/deep-research/`

2. 下次启动会话（或执行 `/new`）后，技能会出现在 Skills 索引中。

## 使用

通过技能系统调用：

```
/deep-research 固态电池最新技术进展如何？
```

或程序化调用：

```
/run-skill deep-research "对比 Rust 和 Zig 在 2025 年的系统编程优劣势"
```

技能以子代理模式运行，独立完成整个研究流程，返回报告文件路径。

## 环境要求

| 要求 | 详情 |
|------|------|
| **平台** | Claude Code / Reasonix（或兼容的 agent 运行时） |
| **工具** | `web_search`、`web_fetch`、`write_file`、`read_file` |
| **模型** | 推荐：`deepseek-v4-pro`；最低：`deepseek-v4-flash` |

## 设计原则

| 原则 | 落地方式 |
|------|---------|
| **先拆解再研究** | 防止对复杂问题给出浅层回答 |
| **言必有据** | 所有事实性主张必须引用来源 URL |
| **以证伪求验证** | 主动搜索反方证据，而非只找确认信息 |
| **迭代而不编造** | 最多 2 轮迭代；失败如实标注，绝不虚构 |
| **输出结构化** | 统一报告格式，便于跨主题对比 |
